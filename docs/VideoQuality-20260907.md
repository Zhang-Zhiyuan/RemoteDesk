# H.264 清晰度与硬件验证（2026-09-07）

## 结论与当前状态

有比“全程 JPEG”更适合清晰、流畅远控的方案，且本机硬件足够进行
1080P 实验：继续使用 H.264 硬编/硬解，但恢复有效的帧间压缩，再考虑
静止后的文字/颜色细节补清。单纯提升编码预设或切换 HEVC，并不能替代
参考帧、丢帧恢复和带宽策略的优化。

**本轮只加入可复现的实验工具，没有修改正式视频策略、安装新版或覆盖
正在运行的 RemoteDesk。GOP30、HEVC 和静态补清均未作为正式功能上线。**
此前未接入捕获路径的 WIC JPEG 实验已撤回，没有留下额外 WIC 依赖。
Windows 回归测试：1,563 通过，11 跳过，0 失败；跳过的实机用例不计入通过。

## 找到的代码限制

- `RemoteViewerClient.LocalViewerCapabilities` 当前显式关闭 `ShortGopH264`；
  中继协商同样不广告此能力。Windows 默认 `AllSamplesIndependent` 为真，
  即 GOP1，每帧独立编码。
- `FfmpegDesktopH264Capture` 只允许 GOP1/GOP2；GOP2 必须严格 IDR/P 交替。
- 主机源帧替换、交互降帧、UDP 发送槽和 TCP/UDP 切换均依赖这些约束。
  将 `-g` 直接改成 30 会违反现有协商/序列校验，可能造成回退、断链或黑屏。
- 当前 NVENC 已使用 P4、低强度空间 AQ、无 B 帧、无 lookahead 和有界 VBV。
  不是“没有使用硬件”，而是画面压缩效率受兼容策略限制。

## 实测

本机 NVIDIA GeForce RTX 2080 Ti，驱动 `32.0.16.1656`，PATH 上的 FFmpeg
`8.0-full_build-www.gyan.dev`。使用合成的浅色/深色代码、中文、细线页面，
1920×1080、60 FPS、每种场景 180 帧。此输入不是用户桌面截图。

H.264 各组均保持 Main/4:2:0、无 B 帧、无 lookahead、相同标称码率
22.3 Mbps 和相同 VBV。GOP30 与当前配置的主要变量是关键帧间隔。

| 配置 | 静态实际码率 | 滚动实际码率 | 静态亮度 PSNR | 滚动亮度 PSNR |
| --- | ---: | ---: | ---: | ---: |
| 当前 H.264 GOP1 | 22.31 Mbps | 22.31 Mbps | 24.49 dB | 24.50 dB |
| 实验 H.264 GOP2 | 22.05 Mbps | 22.13 Mbps | 29.82 dB | 29.57 dB |
| 实验 H.264 GOP30 | 8.66 Mbps | 15.11 Mbps | 41.76 dB | 40.99 dB |
| 实验 HEVC GOP30 | 8.84 Mbps | 13.36 Mbps | 41.08 dB | 40.44 dB |

PSNR 越高，代表这套合成输入上的像素误差越低，不是“清晰度提升百分比”。
参考图已经做过相同的 RGB→NV12 转换，因此此分数**不包括 4:2:0 丢失的
彩色细节**。人工查看同一位置的 100% 解码裁图，也能看到 GOP30 的黑色
细字比 GOP1 更完整。测试图里的少量文字交叠来自生成器，不是解码伪影。

所有 16 组均通过显式 NVENC 编码和 CUVID/NVDEC 解码，帧数完整。
14 组 H.264 还通过了本项目自身的 Annex-B 解析器和 Windows Media
Foundation D3D11 硬解码器，每组实际输出 180/180 帧。GOP1 为 180 个 IDR，
GOP30 为 6 个 IDR。HEVC 没有通过项目解码器测试：项目尚未接入 HEVC。

GOP30 两种场景的离线处理吞吐约 217/195 FPS，本项目硬解码调用 p95
约 12.77/12.70 ms；GOP1 解码调用 p95 约 12.13/11.98 ms。吞吐包含 PNG
读取、格式转换和滤镜，解码调用耗时也不等于完整呈现延迟。这些结果说明
本机具备相关硬件能力，**不构成远程 60 FPS、弱网不卡顿或跨平台兼容保证**。

P5 预设的亮度 PSNR 改善只有约 0.12–0.14 dB；CQ18 的平均码率反而升至
约 24.6 Mbps。因此未把这些小幅、增加成本的参数改动当作正式修复。

## 建议接入顺序与验收条件

1. 增加明确协商的帧间压缩模式，保留旧客户端的 GOP1 回退。先解决参考链
   完整性，再决定正常/弱网关键帧间隔，不把实验 GOP30 固定为所有网络默认值。
2. 源帧替换、队列溢出、主动降帧、控制消息抢占和 TCP/UDP 切换都必须使
   丢失的参考链失效；仅在完整恢复帧后继续发送/解码依赖帧。验证启动、
   丢包、乱序、慢接收端、断线重连和切屏，而不仅测试正常连续播放。
3. 对静止桌面设计有界的高质量/完整颜色补清：优先局部变化，不能每帧
   插入整张 JPEG。补丁必须绑定画面代次，避免覆盖更新的运动画面；旧端
   不支持时不发送。此步骤目前是设计建议，没有实现。
4. HEVC 作为双端探测后启用的扩展。编码端支持不代表 Windows/Android/Linux
   控制端都能硬解该格式、位深和颜色采样；不能强制 H.264 4:4:4。

NVIDIA 的[编码器文档](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-video-encoder-api-prog-guide/index.html)
说明了预设的速度/质量取舍，以及低延迟串流中的参考帧恢复机制。
[解码器能力表](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvdec-video-decoder-api-prog-guide/index.html)
也区分了 H.264 与 HEVC 的颜色格式/硬件支持，不能只按显卡型号假定兼容。

硬件不会提升公网路径本身的带宽。此前中继路径测试吞吐偏低，不能据此
承诺 1080P60；需在正式会话中结合实时带宽和反馈决定画质/帧率。
