## 发现并修正的问题

Windows → Android 两次中转连接均在 150 秒后被测试超时保护结束。第二次采集的
线程栈 `windows-android-hang-stacks.log` 明确显示：

1. 连接初始化持有 `_connectionStateLock`，直接调用异步接收循环。
2. 手机提前发送的屏幕信息已在缓冲区内，异步读取立即完成，因此回调仍在锁内执行。
3. 接收线程同步等待 WinForms 更新屏幕选择；界面线程查询 `IsConnected` 又等待
   同一把连接锁，形成死锁。超时取消关闭了套接字，但无法解开这组线程等待。

修正为将接收、输入及心跳循环排入后台任务，不在启动锁内内联执行；不取消任务
调度，确保连接拥有者的收尾逻辑仍会运行。没有绕过身份验证、取消屏幕代际检查，
也没有放宽输入断言。

新增回归 `BufferedCaptureTargetCallbackDoesNotRunUnderConnectionStartupLock`：
先阻塞查看端首条消息，确保对端屏幕信息提前进入缓冲区，再检查回调不能持有启动锁。
旧代码测试失败，修正后通过；分别见 `deadlock-before-fix.log` 和 `deadlock-after-fix.log`。

## 仍需明确的限制

- 这些是短时功能测试，不保证无 bug、长期无人值守或固定 60 FPS。Android → Windows
  末次采样降到 3 FPS，Windows 被控端日志也有帧率波动，不能宣称流畅性已经全面验收。
- Jetson 被控端硬件编码首帧探测未成功，实际回退 JPEG；Android → Linux 约 22 Mbps。
  Jetson 查看端硬解后仍回读 CPU/MJPEG/Tk，不是零拷贝。
- Windows 测试源把 4K 主屏缩放到 1080p；手机不是全分辨率。三台可共处同一 LAN，
  只是数据强制经过公网，不代表不同运营商/NAT/移动网络切换验收。
- 本轮没有逐项真机重测文件传输、全部快捷键、多显示器、锁屏、Wayland、多机争抢
  或长时间断网；相关自动化与历史记录不能扩大为本轮全场景实测通过。
