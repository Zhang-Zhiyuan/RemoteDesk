## 得到了什么

同一张合成 4K 中文桌面，底图仍是 1080p H.264，再经过正式 Windows MF/D3D11
硬解和 NIS 放大。额外把当前 960×640 原生像素区域分成 128×128 小块，无损压缩后
通过真实 RDK1 认证、AES-GCM 加密的本机 TCP 连接传给实验接收端，再与底图合成。

这次不是把字边缘继续锐化：补齐区域的每一个 RGBA 像素都与原图一致。关闭补清后，
合成结果也与原底图逐像素一致。区域外没有被改动。

| 检查 | 结果 |
| --- | --- |
| 初次补齐视口 | 40 块，87,919 字节压缩像素；含片段和加密记录开销共 93,243 字节 |
| 页面自行改一行文字，没有输入事件 | 4 块变化；先清掉旧字，其余 36 块保留 |
| 新文字补齐 | 4 块，含上述开销共 11,867 字节；与修改后原图精确一致 |
| 迟到的旧文字片段 | 拒绝，不覆盖新底图 |
| 相同内容的新视频帧 | 保留有效细节，不因新的 IDR 把字重新变糊 |
| 关闭后再收到旧数据 | 不重新启用；精确回到原底图 |
| C# 单元测试 | 51 项通过，无失败或跳过 |
| Linux ARM64 真机 Python 接收端 | 89 个事件的接收结果、缓存像素／状态、在途字节与 C# 一致 |
| Java 接收端 | 同样 89 个事件通过；桌面 JDK 17，按 Java 8 目标编译 |

这里的缓存区域按相交块传输，再按视口裁切，因而 40 块覆盖面积略大于视口。
数字来自本地 `artifacts/native-detail-20260914-r5/summary.json`；对照图是其中的
`native-detail-comparison.png`，由上到下为原图、实际硬解/NIS 底图、收到原生块后的结果。
都是 100% 像素裁图，不是把对比图再放大，也不是手机拍照。

## 这轮修掉的问题

- **细节队列饿死。** 实测发现，每次控制消息都清空发送额度，在约 16 ms 的定时器
  粒度下会让细节一直发不出去。改成输入控制优先、最多保留一片额度，并补了回归测试。
- **压缩数据截断漏检。** .NET 8 在已经解出足量像素时，可能接受缺少末尾校验部分
  的 zlib 数据。现在要求精确结束单个压缩成员，拒绝截断、尾随数据和拼接成员；
  Python、Java 用各自解压器独立验证，同批损坏数据也全部核对。
- **旧画面覆盖新字。** 每块绑定会话、视口请求、原生内容版本和底图引用；底图呈现时
  先作废变化块。输入、切屏、尺寸变化、关闭的生命周期也有测试，不只依赖“鼠标没动”。

缓存最多 64 块、4 MiB RGBA；最多两个未完成传输；发送队列限 256 KiB。每片最多
4 KiB 像素数据，按含协议开销的字节数限速，拥塞时暂停，过期或变化块取消。
实现和复现命令见[原型说明](../experiments/NativeDetail/README.md)。

## 不能据此承诺公网已经变快

本机回环连接下，配置 2 Mbps 补图额度，初次发送阶段 464 ms，改字后 32 ms。
这些计时**不含** 250 ms 画面稳定等待、捕获／编码准备、最终合成显示；第二阶段
允许沿用不超过一片的额度。它们不是公网时延，也不能当成用户输入到文字清晰的时间。

当前验证了真实加密传输、真实 Windows 硬解/NIS 读回，以及 CPU 上的精确补图。
尚未测连续视频争用、真实中继、实际鼠标响应、DWM 呈现时延或正式 Linux 窗口。
Java 接收端的通过不等于安卓整机通过：本轮 ADB 没有连接手机。

## 接入正式版还缺哪些环节

1. **让底图和原生块来自同一个捕获帧。** 正式 FFmpeg WGC/DDA 路径目前只向应用
   暴露编码流，视频头也没有原生内容版本。必须补上同源捕获和协商元数据，不能另截
   一张图、靠接近的时间强行覆盖。原型已定义并测试此契约，但未改正式捕获链。
2. **实际 GPU 合成与坐标映射。** 原型保留整幅 CPU RGBA、逐块比较、最后 CPU 合成；
   这不是最终性能方案。还要接入纹理合成、不同 DPI、缩放／平移、旋转、切屏和色彩
   处理，使底图呈现与细节失效成为同一个事务。
3. **三端协商和真实链路验收。** 保留原版放大及 1:1；新模式单独可关，旧端不接收
   未知载荷。补图预算由真实链路余量驱动，再测公网下视频、输入、剪贴板和文件争用。
   分小片本身不能消除共享 TCP 的队头阻塞。

这一步已经证明“传回原生局部像素”在文字上能带来纯放大没有的改善，并跑通了
传输、失效和回退原型；还不能说安装版已经有这个能力。
