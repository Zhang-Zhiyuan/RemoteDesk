# 文字清晰度实测：放大之后应该改什么

2026-09-13。本轮新增隔离实验，没有改动正式视频策略、替换运行中的应用或发布新版。
Windows 和 Linux 真机已测；ADB 当前没有连接手机，不能算安卓实机通过。

后续：[2026-09-14 原生局部补清原型与实测](NativeDetail-20260914.md)，已跑通独立的
加密传输、原生像素合成和跨语言状态校验，尚未接入正式应用。

## 结论

优先做“流畅视频＋原生局部细节补传”。纯放大只能处理收到的像素，不能可靠恢复
先缩小、再压缩时丢掉的中文笔画。有效的帧间压缩也值得接入，但不能直接改成
GOP30：本轮除了验证它省带宽，还测到了周期性关键帧造成的文字清晰度下降。

建议将局部补清和帧间压缩作为两个独立、可协商的改进。局部补清原型不必等待
新视频协议全部完成；先保留现有视频兼容路径，验证原生像素确实及时到达正确
区域，再推进视频参考链改造。现有“新版放大”开关保留，不用更强锐化代替补清。

## 1. 同一张中文桌面的对照

本机 RTX 2080 Ti，驱动 616.56，已安装的 FFmpeg 8.1.2。生成 3840×2160
浅色/深色中文、代码桌面，字体为原生 12/14 像素，属于刻意较难的小字场景，
不是用户桌面截图，也不能代表所有网页、视频和 UI 缩放设置。

采用产品 NVENC P4 / ULL / VBR / AQ 配置，无 B 帧、无 lookahead；统一 BT.709
转换、4 帧 VBV。每种配置有静态、缓慢滚动两组，各 180 帧、30 FPS，并分别
请求 10 / 20 Mbps。这里的静态输入仍连续编码，不等于正式 WGC 静止时的停帧行为。
主矩阵和 GOP2 补测原图解码后的 BGRA32 哈希核对一致；PNG 重新保存后的文件
哈希不同不代表源像素不同，核对结果保存在 `reference-pixels.json`。

下表是请求 10 Mbps 时的**实际码率**及静态最后一帧的固定文字裁区：

| 方案 | 静态实际 Mbps | 文字墨迹 IoU | 墨迹亮度平均误差 |
| --- | ---: | ---: | ---: |
| 1080p GOP1，原版放大到 4K | 10.00 | 0.2740 | 104.31 |
| 同一码流，NIS 放大到 4K | 10.00 | 0.3379 | 101.24 |
| 原生 4K GOP1 | **28.08** | 0.6236 | 66.17 |
| 原生 4K GOP2，实验 | **14.26** | 0.6251 | 65.84 |
| 原生 4K GOP30，实验 | 6.47 | 0.9475 | 13.67 |

IoU 来自固定裁区亮度小于 150 的墨迹掩码，不是 OCR 识字率或“清晰度提升百分比”。
参考是原生 RGB，误差包含缩放、色度采样、压缩及实际呈现转换。
已人工查看原始像素裁图：NIS 有限改善边缘，但很多笔画仍缺失。

原生 GOP1/GOP2 明显超过请求码率，因此不能说所有行都在相同的实测带宽内。
NVENC 没有报告编码错误，不能把配置里的 `maxrate` 当作实际链路硬上限。
20 Mbps 请求下，1080p GOP1 仍有明显小字损失；原生 GOP30 最后一帧更好，
但这不能替代下面的逐帧检查。滚动时原生 GOP30 实际约 6.72 / 10.40 Mbps
（对应 10 / 20 Mbps 请求），这里只比较码率，没有把静态文字指标套到滚动帧。

## 2. 最后一帧好看，不代表播放时稳定

补测了每个模式 20 个明确时间戳匹配的帧，覆盖首帧、后续 P 帧和 IDR 边界。
10 Mbps 请求下原生 GOP30 的文字墨迹 IoU：

| 帧号（从 0 开始） | 类型 | IoU |
| ---: | --- | ---: |
| 29 | P | 约 0.93 |
| 30 | IDR | 约 0.70 |
| 31 | P | 约 0.79 |
| 59 | P | 约 0.95 |
| 60 | IDR | 约 0.70 |
| 179 | P | 约 0.95 |

这说明当前参数下存在“清晰—变糊—逐渐清晰”的周期。需要联合调整关键帧
策略、码率分配和静态细节保持，不能只比较最终截图。GOP2 在本次 10 Mbps
请求下减少了实际用量，但墨迹指标仍约 0.62，不能作为文字问题的完整修复。

GOP30 最大单帧 163,128 字节。假设可用速率正好是 10 Mbps，仅发送这些字节
就至少需要约 130.5 ms；这是计算下限，不是测得的公网延迟。平均码率下降
不代表关键帧不会堵塞链路，还要验证突发、队列、丢帧和交互优先级。

## 3. Windows 硬解没有在这组测试中多等一帧

四种静态编码配置（1080p GOP1、原生 GOP1/GOP2/GOP30）、两个码率、每组两轮，
共 16 轮。每轮 60 次输入，按运动／2 Hz 静态／运动节奏提交给实际 MF/D3D11
解码器：全部返回 60/60 输出，均带明确输出 PTS，最大输入序号滞后为 0 帧。
主矩阵解码时间 p95 约 1.08–2.27 ms，单次最大约 18.62 ms。

计时是完整 AU 提交到匹配时间戳的 GPU 纹理返回。调度间隔从上次调用结束算起，
不是严格固定 30 FPS 播放；不包含桌面捕获、网络、DWM 或屏幕发光延迟。
没有加入额外 drain 帧或伪造未来时间戳。

三个原生 GOP 模式又各做三轮冷启动／显式丢帧通知／重置恢复，每轮 48/48 输出。
有依赖的模式会拒绝无参考 P 帧，等待 IDR 后恢复。这里模拟的是解码器收到缺口
通知，不是实际丢包、发送队列覆盖或传输切换测试。

现有 Windows 查看端仍关闭 GOP2 广告，捕获、发送槽和接收验证只支持 GOP1 或
严格的 IDR/P 对。GOP30 必须有新协商和参考链处理，不能因为本机硬解通过就
打开三端默认开关。

## 4. 原生补清必须按区域、有预算

对合成原生 RGB 桌面分块 PNG 编解码，逐行比较还原 RGBA；两种块大小全部精确
一致。改一行文字、当前 960×640 可视区域与整个 4K 画面的成本如下：

| 方块边长 | 全屏编码字节 | 可视区域相关块字节 | 单行改动相关块字节 | 全屏编码／解码复制耗时 |
| ---: | ---: | ---: | ---: | ---: |
| 128 | 998,671 | 79,694 | 10,306（4 块） | 149.50 / 68.69 ms |
| 256 | 889,390 | 85,601 | 19,812（2 块） | 115.94 / 36.52 ms |

这是顺序 CPU 测试，包含块复制、PNG 编码／解码复制，不包含真实捕获、变化
检测、加密、网络或 GPU 合成。可视区域统计包含所有相交块。

若**假设**剩余 2 Mbps 用于细节，128 像素方案的发送下限约为：整屏 4 秒、
可视区域 319 ms、单行改动 41 ms。256 像素整屏约 3.56 秒。这还没加 RTT 和
排队，说明频繁整屏补一张高清图不合适，也不能承诺每次 200 ms 内全屏变清。
128 对小改动更省，256 对本例的首次全屏更省；块大小还需用实际文档和图片验证。

## 5. Linux 的瓶颈不只是硬解能力

在 Jetson AGX Orin 真机上导入已安装 1.0.22 的实际解码类，输入上述合成 4K
码流。没有改动应用安装、显示会话或网络配置。

- 120 ms 等待、4 个 correlation 上限：NVV4L2 后端在第 5 次尝试时溢出，
  0 输出；GOP1/GOP30 都发生。软件后端分别返回 46/47 个输出。
  独立重复一次，两个后端的这组计数和队列结果均复现。
- 1000 ms 诊断等待：NVV4L2 两组各返回 46/48，留下 2 个在途帧；软件各 48/48。
  这说明不是单纯格式不支持，但长等待不是低延迟修复。FIFO 对应关系不等于
  视频内嵌时间戳，这些延迟不能当成精确呈现延迟。

随后以整文件输入、保留安装版后端参数作控制试验，全部处理完 180 帧：

| 后端 | 仅解码、空输出 | 解码＋现有 JPEG 转换、空输出 |
| --- | ---: | ---: |
| NVV4L2 硬件 | 59.68 FPS | 11.29 FPS |
| 软件 | 63.84 FPS | 11.67 FPS |

时间包含进程启动，还没算 JPEG 读回 Python、Tk 缩放和实际显示。与 paced 测试
不同，这是文件输入吞吐，不能换算成单帧实时延迟。它把问题进一步缩小到
JPEG 兼容转换路径：应继续验证原生呈现和避免重复转换，而不是扩队列攒旧帧。
产品已有原生 mpv 路径及失败回退；本轮没有运行图形会话，因此不能说所有 Linux
会话都只有 11 FPS，也不能把这个结果当作 mpv 性能测试。

## 接下来怎么实现

1. **原生局部补清独立原型。** 源像素必须取自下采样和 NV12 转换之前。优先
   当前视口和正在阅读／编辑的区域；停稳的局部才补，不能把“无鼠标输入”
   等同于画面静止。预算不足就延后细节，输入和流畅视频优先。
2. **补丁生命周期先于默认上线。** 绑定屏幕、尺寸、会话代次和每块内容代次。
   滚动、编辑、切屏、缩放、重连时失效；拒绝迟到块。低清视频的新帧不能
   随意擦掉仍有效的细节，也不能让旧细节盖住新文字。用可核对序号的合成
   页面测试，像素一致性和旧字残留都要有断言。
3. **限制内存、带宽和等待。** 原生图块采用可检查尺寸的独立消息，限制最大
   解压像素和在途数量；小块调度，拥塞时取消未发补丁。共同经过中继时也须
   测输入／剪贴板／文件竞争，分块本身不能消除共享 TCP 的队头阻塞。
4. **帧间视频单独接入。** 不固定所有机器为 1080p，也不固定 GOP30。链路和
   解码允许时优先保留原生分辨率；不足时降视频成本并让视口补清负责小字。
   在源帧替换、UDP 丢失、主动降帧、TCP/UDP 切换、重连时正确作废参考链。
   关键帧后的清晰度波动和突发发送成本必须进入验收。
5. **跨平台兼容与回退。** 新能力双端协商；旧端保留当前路径。Windows 验证
   不同显卡和锁屏恢复；Linux 比较实际原生呈现与兼容路径；手机接回后验证
   硬解、横竖屏、缩放视口与发热。保留现有放大和 1:1，避免把算法参数堆到 UI。

手机全屏缩小显示整张 4K 桌面时，屏幕物理像素仍然有限；局部放大时按视口
取原生细节，比对整个低清底图再次锐化更有意义。

文字模糊”或“画质不降且没有延迟”。
