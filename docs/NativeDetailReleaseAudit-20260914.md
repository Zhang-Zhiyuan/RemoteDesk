## 实测和修复

发现一个快速开关时的资源问题：后台准备尚未完成，关闭／改尺寸会丢掉任务引用，
下次开启又排一个初始化任务。用真实 D3D11 设备挂起准备线程，新增的两项测试在
修复前都失败，报告保留为 `tests/rapid-toggle-before-fix.trx`。

现在每个 presenter 最多运行一个初始化任务；仅新的**显式本地开启请求**可以复用
尚未完成的、与窗口尺寸无关的着色器／纹理准备。RenderTargetView 仍属于当前窗口
代次，后台不持有旧后缓冲区。关闭会立即撤销发布授权，任务迟到不能自行重新开启。
任务完成与状态发布使用同一把锁，避免在旧任务即将退出时吞掉一次新的开启请求。

实测连续开关和改尺寸 20 次，仍只有一个准备任务；分别验证了最终保持开启、最终
关闭、继续重新开启及最后窗口的实际 Draw。底图不会等待准备线程。

## 60 Hz 显示测试

新增 `--native-detail-pacing`，实际运行 MF 硬解和 D3D11/NIS／原生纹理合成。原生
参考图为合成 4K 中文桌面，码流为对应的 1080p H.264。绘制 4K 后缓冲区，在探针自己
的 960×600 可见窗口预览，不接管其他窗口、不发送系统输入。

每轮 7 个阶段、每阶段 120 帧，另有 30 帧底图预热：底图、冷初始化、缓存补清、底图、
繁忙跳过、连续文字变化、底图。使用本地一帧的截止时间，而非上一轮像素正确性探针
中人为给定的 2 秒预算。测量循环不加 GPU 查询等待、Flush 或像素读回。

第 3、4 轮均为 870 次成功硬解／呈现，未错过调度时隙、未超过 CPU 提交截止时间。
冷启动前 6 帧只显示底图；缓存和文字变化阶段各 120 帧成功补清。繁忙阶段 120 帧
全部跳过补清，纹理上传 0。初次只上传 40 块，后面 10 次改字共上传 40 块。
第 5 轮另加了原生窗口可见性检查，重复上述全部阶段也通过。

第 4 轮 `Present` 调用的 CPU 耗时如下（**不是 GPU 完成或端到端时延**）：

| 阶段 | 中位数 | P99 |
| --- | ---: | ---: |
| 开始时的底图 | 0.103 ms | 0.467 ms |
| 冷启动及逐帧补齐 | 0.123 ms | 1.429 ms |
| 已缓存补清 | 0.106 ms | 0.625 ms |
| 不断修改文字 | 0.118 ms | 0.752 ms |
| 结束时的底图 | 0.096 ms | 1.164 ms |

前两轮使用普通 Sleep 驱动时，调度本身会迟到十几毫秒；少量 CPU 提交超时帧均未做
增强。改用产品已有的高精度等待器后重测，原始报告保留，未把探针的定时抖动当成
产品超分故障。原生变化检测、压缩等夹具准备耗时单独记录，**不包含在显示期限内**。
输入、积压、拥塞标志是明确的模拟压力，不是实际用户输入 ACK。

另跑独立 GPU 像素探针：40 块与原图精确匹配、4 块文字更新、8 组几何、拒绝错误
底图引用及异常后恢复原底图均通过。该轮 GPU 中位数为底图 0.915 ms、缓存补清
1.020 ms，差约 0.105 ms。GPU 成本并非零，前后轮数据也不应混作同一个计时范围。

## 公网 Windows → Linux 功能实测

两轮使用现有已验证的公网中继配置，经真实 TLS/TCP 中继到物理 Linux 机器上新建的
独立 Xvfb 测试主机，没有直连回退、没有重启中继或替换已安装的远端。

11 项检查全部通过：错误密钥拒绝、能力及画面协商、切屏响应、中文／emoji 剪贴板、
旧时间戳目录打包、重复命名／空文件／目录上传、文件回传、JPEG→H.264、H.264→JPEG、
新会话替换旧测试会话、同一客户端两次重连。Linux 端另外核对了真实落盘文件 SHA-256、
压缩包中文文件和剪贴板内容。它测试的是既有远控协议，**没有传输新的原生补清块**。

密钥只走进程内存／stdin，没有写进参数、报告或源码。临时主机使用随机设备标识，
不替换用户设备目录项。本机系统剪贴板和真实 Linux 桌面均未修改。
