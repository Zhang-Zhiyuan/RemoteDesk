# H.264 中继积压控制

本轮为 Windows 普通 H.264 / TCP 增加接收回执。原来只能看到写入本机 socket 的耗时，
中继后半程堵塞时仍可能持续塞入旧画面。现在按照对端实际收完的数据释放发送额度，
并把发送分散到一个往返周期内，避免回执集中到达后突发发送。

未发送的独立帧直接跳过，不等待、不排队，不重新压缩或降低每帧的编码画质。
不切换 JPEG。丢弃尚未发送的帧会影响低带宽时的帧率，因此不承诺所有场景都更高 FPS。
分辨率、原生补清和 GPU 放大算法没有在这轮修改。

## 边界

- 双方协商后才使用新记录。旧 Windows、Linux、Android 保持原有视频格式。
- 只处理独立 H.264 帧；UDP、原生补清、依赖参考帧的视频链沿用各自规则。
- 回执确认收包，不代表完成硬解或显示。输入和心跳不需要等待视频额度。
- 无回执时最多发送两个初始帧，不能持续向中继积压。有效回执必须精确匹配发送记录。
- 未确认记录最多 128 个、通常不超过 8 MiB；空窗口可单独通过一个更大的关键帧，
  仍受协议帧大小限制。场景变大时不会因旧的小额度死锁。
- 编码器重启、切屏、TCP / UDP 切换保持同一连接的序列；重连重新开始。
- 软件及锁屏备用采集在没有额度时仍遵守采集周期，避免空转编码。

## 限速对比

使用加密 TCP、限速转发器、48 KiB 固定测试载荷、30 Hz 来源。载荷逐帧校验不变，
回执额外延迟 300 ms；正向限速依次为 850 / 200 / 850 KiB/s。
下表来自 `artifacts/reliable-feedback-20261117/r4b/comparison.json`。

| 阶段 | 原逻辑接收 FPS | 新逻辑接收 FPS | 原逻辑 P95 帧龄 | 新逻辑 P95 帧龄 |
| --- | ---: | ---: | ---: | ---: |
| 初始 | 10.00 | 8.50 | 494.8 ms | 375.3 ms |
| 带宽下降 | 3.63 | 2.63 | 1473.2 ms | 506.5 ms |
| 带宽恢复 | 3.63 | 8.25 | 139.2 ms | 313.6 ms |

这是从生成测试载荷到完整收到记录的时间，不包含解码、显示或用户操作，
也不是欧洲公网测量。恢复阶段以更高接收帧率换取了部分余量，不能把所有指标都描述为改善。
早期 r1–r3 的低带宽恢复过于保守，后续加入独立样本重估、发送节奏和完整帧额度处理。

另做了无人工限速 / 延迟的加密 TCP 对比：新旧逻辑各发送、接收 360 帧，
稳态均为 30 FPS，新逻辑没有跳过帧。P95 帧龄约 15.3 / 14.8 ms，
这个小差异不作为性能提升结论。证据在同目录 `healthy/comparison.json`。

## 实际采集与兼容

使用真实 Windows 桌面和临时被控端，经 150 KiB/s 加密 TCP，故意延迟 1.2 秒发送视频协商：
旧能力模式和新反馈模式均收到 5 张 H.264 帧、5 次心跳，首张画面成功解码，JPEG 为 0。
新模式收到 5 个连续追踪序列。两个模式都触发了现有 WGC 停帧恢复，再进入 DDA / MF H.264；
这项测试验证恢复后可继续传输，不能当作没有捕获停顿的证据。

新增回归覆盖无回执、非法 / 重放回执、额度上限、较大关键帧、发送节奏、慢链路重估，
以及真实 `RemoteViewerClient` 收包回执和重连序列清零。Java / Python 检查最高能力位
为有符号 int32 时仍保留既有功能。手机真机和 Linux 新反馈链并未实现或实测。
