## 本轮实现

`D3D11DesktopSource` 从一次 Desktop Duplication 取帧取得原图及脏区，
将同一张 GPU 原图交给编码和局部读回。最多允许三张尚未释放的快照，取帧使用零等待。
暂不接管旋转、变更或断开的显示器；失败应由后续会话集成退回现有路径。

`NativeSurfaceDamageTracker` 对脏区和移动区域保守地更新 128×128 块版本；
元数据丢失、越界或超过上限时全部失效。即使某张已采集画面没发出去，后续完整版本表
仍保留它的变化。快照不会与后来更新的数组共享可变存储。DXGI 的变化区域语义见
[微软 Desktop Duplication 文档](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)。

`MediaFoundationD3D11H264Encoder` 在 GPU 上缩放并转 NV12，交给硬件 MFT；
仅允许一张输入在途，不以第二张输入或 drain 催出前一张。每张输出实际检查 SPS/PPS/IDR
和输入时戳，初始化、错误和驱动引用都有独立生命周期。目前只支持这条全 IDR 合约，
没有因此打开原先关闭的正式 GOP2 开关。驱动接受设置不等于满足低延迟要求，仍需实测；
相关接口合约见 [低延迟模式](https://learn.microsoft.com/en-us/windows/win32/medfound/codecapi-avlowlatencymode)。

`D3D11NativeRegionReadback` 每张原图最多复制两块、共四个 staging 槽，显存 256 KiB；
不整屏下载、不 Flush、不等待 GPU 完成。使用
[DO_NOT_WAIT](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_map_flag)
读回，忙则稍后再看。没有明确的本地时间余量，或输入／底图／传输繁忙时直接跳过。
RGBA 转换放在 GPU 上下文锁之外；关闭清空任务，但不能用清空来绕过单帧额度。
这不是硬件 API 调用“绝对零耗时”的保证，正式调度仍需使用真实的网络和输入压力。

实测发现并修正了借用引用问题：Vortice 的纹理 `Device` 是缓存包装对象，不能作为
临时对象 Dispose；否则同一张原图交给第二个消费者时会被错误地判为来自别的设备。
新增硬件测试覆盖同一纹理反复编码、同时读回、取消和重复释放。

## 实际运行结果

硬编码能力探针使用合成 NV12 GPU 纹理，NVIDIA MFT 连续 120 张输入保留了精确时戳，
且每张不依赖下一张输入即可输出。高精度轮询下该轮观察到的编码中位数约 2.30 ms。
AMD 的注册项在这台机器上激活失败，保留了失败记录，没有把它算作可用硬编。

新采集探针打开自己独占的固定 2560×1440 测试窗口，以 DDA 真正采集它，再在 GPU
缩到 1280×720、硬编码、硬解和呈现。增强从同一 GPU 快照读取原生文字块。
预览窗口是缩小显示，后缓冲区为 2560×1440；不是声称预览窗口物理像素为 1:1。

第 6、7、8 轮各 240 帧全部完成，原生块全部通过逐像素校验，三轮均取到了三块新文字。
输入繁忙阶段各 30 帧，原生绘制／上传均为零。第 9 轮也通过：12 个准确的读回块，
100 帧启用增强，30 帧繁忙跳过。最终代码的第 10 轮再完成 240 帧，15 个原生读回块
全部准确，其中三块为修改后的文字；101 帧增强、30 帧繁忙跳过。

第 9 轮从 GPU 快照发起复制后到解码／显示 CPU 提交的观察值：

| 阶段 | 帧数 | 中位数 | P95 |
| --- | ---: | ---: | ---: |
| 暖机后的底图 | 50 | 3.56 ms | 5.10 ms |
| 已缓存补清 | 60 | 3.85 ms | 5.12 ms |
| 模拟输入繁忙 | 30 | 3.82 ms | 5.64 ms |
| 关闭后的底图 | 25 | 4.10 ms | 5.70 ms |

暖机后没有超过一帧 16.67 ms 的提交。**这不是公网、真实输入 ACK、DWM 或光子延迟，
也不是与已安装 FFmpeg 方案的端到端 A/B。** 数字包含轮询和线程调度，不是纯 GPU 时间。

早期探针每次编辑都整窗重画，让同线程的输出轮询迟到约 50 ms；第 6～8 轮各有一次，
这些帧均未做增强。随后改为仅重绘实际变化的文字／动画区域，并记录绘制时间；
第 9 轮夹具单次重绘最大 4.31 ms。逐像素校验也移到测量循环结束以后，不污染延迟样本。

另有第 5 轮一次原生块与两个夹具都不匹配，之后未复现。当时没有保留错误块像素，
不足以断定是采集、窗口内容变化还是校验问题；没有删掉或改成通过。后续探针已增加
失败块、参考块及对应帧编号的保存，正式接入前仍需继续压力复现和定位。

## 回归与实机范围

- Windows 全量非硬件回归：2,080 通过、六项真实输入场景未配置而跳过，见 `windows-full-final.trx`。
- 新采集边界／版本测试 41 项通过；原生协议测试 53 项通过。
- 新硬件测试四项、原生合成测试六项通过，包括 SDR 色条、同源双消费者、额度、取消及重建。
  另运行硬件分类套件，并单独显式启用旧 FFmpeg DDA smoke，通过。
- Linux/中继 Python：567 项运行，563 通过、4 跳过。
- Android Debug、Release 各 613 项全部实际重跑通过；两个 lint 均无错误。
  Debug 有六项、Release 五项已有警告，涉及偏好持久化、调试清单合并和界面字符串。
- 真实公网 Windows→物理 Linux 再跑一轮：11 项通过，220 帧（203 JPEG、17 H.264）。
  验证中文／emoji 剪贴板、文件 SHA-256、目录／空文件、模式切换、接管和重连。
  **它运行的是既有协议，不是新的原生补清传输。**
- ADB 未发现手机，不能把 JVM 单元测试等同于手机真机通过。

测试没有替换安装版、改根目录路由、重启中继或读写本机系统剪贴板。Linux 临时目录
`/tmp/remotedesk-feature-34pvPifr` 已在确认进程退出、证据取回及路径校验后删除；
本地报告、合成文件及源码归档保留。
