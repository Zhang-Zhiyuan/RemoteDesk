# 补清变化判定修复

历史记录；后续正式接入及反馈调度修复见[正式会话实测](NativeDetailHost-20260914.md)。

本轮直接处理上一轮发现的采集问题，没有发布或覆盖现有安装版。

## 粗脏区导致补清永远不触发

此前采集 r13 的 236 帧都被 DXGI 报为大片变化，静态文字不断重新等待 250 ms。
现增加 `D3D11NativeDamageRefiner`：GPU 对比当前与上次提交的**同源原生纹理**，
逐像素检查请求区域的 RGB，不用有碰撞风险的内容哈希，也不整屏下载。
一次最多 64 块、一个待处理源帧，CPU 只读最多 256 字节的变化标志。

`NativeSurfaceContentTracker` 只接受精确源帧／参考帧配对；版本不能倒退。
像素确实改变时，即使脏区元数据称它未变，也会使旧块失效。
请求区域缺少当前比较证据时同样失效，不能仅凭“未报告变化”保留旧补清。
丢帧、缺失结果、区域变更、单比特变化、边缘小块和随机变化序列均有回归测试。

基础编码先提交。比较在编码工作期间非阻塞轮询，基础输出到达后**不等比较结果**。
已经完成的精确结果不会仅因后续 CPU 调度迟到而被丢弃；呈现仍独立遵守当前时间预算。
没有输入／底图／传输余量时不提交比较。GPU 批次需要一次异步命令提交，
不是等待 GPU 完成，也不是清空视频编码器。相关合约见
[D3D11 Flush](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-flush) 和
[非等待 Map](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_map_flag)。

失败记录仍保留：r14／r15 只在基础输出到达时读取比较结果，全部来不及；
r16 改为编码期间轮询后通过。r17 去掉命令提交后又出现饥饿，故没有采用该改动。
r18／r20～r23／r28 的强制整屏变化测试均通过，r19 的正常脏区测试也通过。

## 像素核验与测试图

增加真实整窗反复重绘测试。r24 暴露测试代码每次转换大型 PNG，使采集轮询线程
被 GDI+ 绘制占用至多约 88 ms；已改为测量前准备不透明位图，并双缓冲绘制。
r25 捕获到明确的像素不匹配：新绘制调用按图片／窗口 DPI 的物理尺寸缩放，
参考文字被放大。已改成源、目标均明确的像素矩形，且采集前逐行核验准备后的图像。
`DrawImageUnscaled` 并不承诺原始像素尺寸，见
[微软尺寸说明](https://learn.microsoft.com/en-us/dotnet/api/system.drawing.graphics.drawimageunscaled)。

r26／r27 的整窗重绘与 r28 的强制整屏变化均通过；每轮 240 张真实基础帧，
分别 12／9／9 块准确读回，均包含 3 块编辑后的文字，并验证 30 帧输入繁忙时不叠加补清。
失败时仍保存实际块、参考块和源帧诊断，不放宽像素误差断言。
**旧 r5 没保存原始异常像素，不能据此追认它与 r25 是同一原因。**
当前版本以精确像素变化判定和逐像素读回测试约束该路径，不再仅依赖脏区推测正确性。
最终 r29（整窗重绘）／r30（强制粗脏区）再次通过：各 240 帧、9 块准确读回，
均有 3 块编辑后的文字和 30 帧繁忙跳过；120 次比较全部完成，增强分别出现在 106／105 帧。

## 开销与回归

本机 RTX 2080 Ti 独立微基准：6／64 块、静态／每块单比特变化，共 360 次比较全部正确。
每组去掉 10 次预热后，GPU P95 约 0.05～0.06 ms；CPU 提交 P95 约 0.22～0.34 ms。
真实采集 r28 中，比较提交、轮询及版本提交的 CPU 总耗时中位数 0.188 ms、P95 0.322 ms。
这不是“零成本”，也不是公网输入到画面的端到端延迟。

Windows 最终全套：**2,118 通过、6 项外部真机夹具跳过、0 失败**，
见 `artifacts/native-detail-refinement-tests-20260914/windows-complete.trx`。
硬件组与变化判定组共 37 通过，其中 25 项硬件测试启用了真实执行开关，
其余 12 项判定测试已计入 Windows 全套。
真实 Windows 查看器的加密 TCP 回环 r8：139 帧、63 次原生 GPU 绘制，
8,192 个输出像素校验、输入后失效、重新请求、缩放和关闭检查通过。

全套第二次运行也暴露了原有中继测试的真实竞态：先分配再释放端口，随后启动 Python，
期间端口会被另一个回环测试占用。该轮出现中继绑定错误和另一项认证超时，
记录在 `windows-full-final.trx`，未删除。现由 Python 中继直接绑定系统分配的端口，
监听成功后才通知测试端，并断言端口仍被独占；不再探测已失去所有权的候选端口。
只改测试启动方式，仍执行真实中继入口，生产配置／TLS 校验没有放宽。
相关 3 项检查修复后通过，加入端口所有权断言后又连续 5 轮通过；
此后两轮完整回归分别 2,117／2,118 项通过，新增项是请求区域缺失证据时的失效保护。
