## 清晰度结果

底图仍由正式 MF/D3D11 硬解和 NIS 放大；原生 RGBA 小块直接上传 GPU 稀疏纹理阵列，
在同一帧的底图上合成，不再用 CPU 拼接整幅输出图。它不是神经网络猜字。

实测的 4K 中文文字区域：40 块补齐后，每个像素与原始截图一致；页面改一行字只需
更新 4 块，其余 36 块不重复上传。合成限定在当前视口，外面仍是原底图。

对照图：本地 `artifacts/native-detail-gpu-20260914-r4/native-detail-gpu-comparison.png`。
从上到下是原生文字、真实硬解/NIS 底图、GPU 补清结果；均为未缩放的像素裁图。

| 检查 | 实测结果 |
| --- | --- |
| 40 块首次上传 | 每帧最多 2 块，20 次呈现逐步补齐；第 21 次确认无重复上传 |
| 4 块文字变化 | 分 2 次呈现上传；其余缓存保留 |
| 上传尚未轮到的变化块 | 立即失效，显示底图，不保留旧文字 |
| 错误／缺失底图时间戳 | 不合成，逐像素等于底图 |
| 关闭／合成后注入异常 | 精确恢复同一底图，不重置解码器 |
| 奇数边缘、稀疏缺块、裁切、黑边及 125%／150%／200% 几何 | 8 组与独立 CPU 采样参考对比，最大 RGB 误差 1；区域外误差 0 |
| 大于 2 倍的原生缩小 | 跳过补清，沿用现有底图滤波 |

纹理阵列 4 MiB，索引图 16 KiB；额外保留有界上传暂存和只读块引用。重用暂存数组，
不在每块上传时分配 64 KiB 新数组。只有被允许的增强帧才提交补清上传和 Draw；
显示路径没有为补清增加 CPU 读回、Flush、等待 GPU 完成或等待完整视口的操作。
这些描述不等于显卡驱动永不阻塞或硬件成本为零。

## 不让补清挡住底图

用户要求：不能为了清晰而让操作更迟钝。因此此入口采用以下约束：

- **默认拒绝增强。** 没有显式本地渲染预算，即使传入了原生块，也只显示底图。
- **初始化不在 Present 中等待。** 着色器编译和纹理阵列创建在后台进行；调用方只能
  在启用时发起准备，不能在逐帧路径等待该任务。资源未就绪时继续显示底图。
- **输入、积压底图、网络拥塞优先。** 任意标志成立就跳过该帧增强。不清掉仍有效的
  缓存，所以余量恢复后不必全部重新上传。
- **按本地单调时钟检查截止时间。** 目前要求至少 2 ms 余量，在上传前、索引更新前、
  Draw 前重新检查。2 ms 是保守的准入阈值，**不是已经验证的 GPU 最坏耗时保证**。
- **限量上传。** 每帧最多 2 块，即最多 128 KiB 纹理上传，另有小型索引和常量更新。
  没补齐也照常呈现底图；所有旧块先失效，再考虑新块的上传额度。
- **生命周期隔离。** 关闭、改尺寸、销毁会让旧准备任务失效，迟到的结果不能重新
  启用。后台任务不持有交换链后缓冲区，避免它阻止 ResizeBuffers。

调用者传入 `nativeDetails: null` 表示这帧不补清；彻底关闭用 `DisableNativeDetails()`。
重新启用或改尺寸后需要新的显式准备。网络包不能触发准备或启用。

GPU 冒烟测试故意挂起准备线程，确认底图先返回，关闭／改尺寸／销毁先完成；再放行
后台线程，确认旧任务不能恢复资源。它检验的是等待关系，不是用一次很短的执行时间
来宣称所有机器都无延迟。

## 实测开销和还没达到的验收条件

RTX 2080 Ti、4K 输出、同一个硬解底图，预热后每组 30 个 GPU 时间戳样本：

| 路径 | GPU 中位数 | GPU P95 |
| --- | ---: | ---: |
| MF/D3D11/NIS 底图 | 0.736 ms | 1.548 ms |
| 同底图 + 已缓存的局部补清 | 0.823 ms | 1.620 ms |

本轮中位数差约 0.087 ms，**不是零，也不是端到端输入延迟差**。计时不包含初始化、
DXGI 等待、Present、DWM 扫出、网络、读回和首次上传。此前三次试跑的中位数差约
0.07–0.23 ms，P95 随负载波动，不能拿某轮较低的 P95 宣称补清使显示变快。
本机仍有已安装 RemoteDesk 的正常捕获任务在运行；没有为了跑分停止它，因此这也不是
独占、固定频率的显卡实验。探针结束后仅退出自己创建的进程，不干扰原来的远控。
像素正确性探针使用人为给定的 2 秒准入预算；这不是正式帧截止时间策略的验收。

目前尚未接入实际输入队列、解码积压和链路余量估计。正式接入必须验证输入到应用
确认、呈现帧龄和 P95/P99 没有可测退化，也不能因补清多缓冲一帧。余量不足就不做。
共享 GPU 的争用、驱动调用内部阻塞、已提交上传都不能靠一个截止时间检查完全消除。

## 同源连续捕获实验

新增探针创建自己的合成测试窗口，先用 PrintWindow 得到一份不可变 RGBA，再把
**同一份像素**交给持续运行的 NVENC 和原生块比较器。每帧携带来源序号，严格限制
编码器只有一个未返回输入；RTP 序号／时间戳、解码 PTS，以及画面中的条码分别验证
捕获、编码、解码、显示的对应关系，不用近似时间或只凭 FIFO 强行配对。

底图和细节通过本机真实 RDK1 认证、AES-GCM TCP 连接发送，再经正式 MF/D3D11/NIS
和新增 GPU 合成入口。第 7 轮结果：

- 134 帧捕获、硬编、加密传输、硬解和显示条码全部匹配。
- 54 帧完整原生视口逐像素匹配；页面自行改字后，迟到的旧文字片段被拒绝。
- 134 次模拟优先控制检查通过；这是探针控制记录，不是实际鼠标应用确认。
- 细节片段含外层开销共 229,094 字节，过期或淘汰队列项 0。

早期探针一次预压缩全部 40 块，遇到慢速抓图和串行发送时会过期重做；改成仅预备
2 块小窗口，配合重复查询和队列回归测试。此优化不改变线格式或接收契约。

**这条 PrintWindow 路径不能用于正式低延迟模式。** 本轮抓图本身中位数 77.70 ms，
含 RGBA 准备共 85.91 ms；比较 1.43 ms；编码桥接 12.76 ms（含上传／转换／RTP，不是
纯编码器耗时）；串行测试循环 108 ms。首次完整补齐约 8.05 秒、改字后约 1.61 秒，
包含每帧只发一片及整帧验证读回等探针限制，不能当作正式 2 Mbps 链路补图性能。
这个实验只证明同源关联和连续更新正确；没有替换现有 WGC 零拷贝捕获。

## 范围和下一步

要上线还需从同一个 WGC/DDA 原生表面分支生成内容版本与局部像素，避免新增慢抓图；
实现正式会话协商、旧端回退、底图失效与显示事务，以及真实链路和渲染预算来源。
共享 TCP 已经在途的细节片段仍可能阻塞后续控制，分片本身不能保证输入零增时。
当前没有改正式消息类型或占用新的能力位。

这轮 ADB 没有手机连接，没有声称安卓整机或三端互联通过；Linux 真机与 Java 的
89 个互操作事件结果来自上一轮。显示方向还需分别接入并测真机、旋转、HDR、不同
显卡驱动和持续温升，不能把桌面 JVM 或本地 GPU 探针当成这些验收。

复现命令见[探针说明](../experiments/VideoQualityProbe/README.md)。本轮证据目录：

- `artifacts/native-detail-gpu-20260914-r4/`：GPU 像素、几何与计时。
- `artifacts/native-detail-live-20260914-r7/`：同源连续捕获的每帧记录与原图。
- `artifacts/native-detail-integration-tests-20260914/`：单元和硬件测试 TRX；后缀
  `paced` 为加入延迟准入和分帧上传后的版本，较早报告保留作对照。

最终构建 0 警告、0 错误。Windows 回归 2,039 项通过、1 项外部主机输入测试因未配置
而跳过；显式启用硬件测试后 10 项通过；便携原生块协议／缓存／调度测试 53 项通过。
三组均无失败，最后一次 Windows 和 GPU 报告分别为 `windows-regression-paced-final.trx`
与 `gpu-smoke-paced-final.trx`，便携测试为 `detail-core-paced.trx`。

所有窗口、编码器和回环监听仅属于探针，结束后释放；未操作其他应用或真实远端。
