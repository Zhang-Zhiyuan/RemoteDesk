# 用 4K 屏幕看原生 1080p 远程桌面

2026-11-27，在 Windows 和 RTX 2080 Ti 上用 RemoteDesk 的实际硬解码器和显示窗口测了原生 1920×1080 桌面。4K 查看区域为 3840×2160 个物理像素，刚好放大两倍。下面的图片都是原始像素裁图，打开 PNG 并按 100% 显示，可以避开浏览器二次缩放。

## 其他工具公开了哪些做法

- ToDesk 提供办公模式、文字边缘锐化和可选的 4:4:4 真彩。它把原始比例 1:1 列为排查模糊的一步，便于区分传输和窗口缩放的影响。[画面模糊排查](https://www.todesk.com/helpcenter/solo-475.html) · [性能与真彩](https://docs.todesk.com/special_superperformance.html)
- 向日葵建议用同一处小字核对被控端分辨率、文档字号和窗口比例。它特别提到真彩有助于保留彩色链接、批注和细线的边缘。[向日葵细小文字说明](https://sunlogin.oray.com/news/62643.html)
- 微软 Azure Virtual Desktop 的软件混合编码会分别处理文字、图片和视频。TurboVNC 则公开了另一种做法，用户停止操作后，可以重新发送先前有损传输区域的无损图像。这两种设计都给文字保留了独立的传输方式。[微软图形编码](https://learn.microsoft.com/en-us/azure/virtual-desktop/graphics-encoding) · [TurboVNC 的无损刷新](https://turbovnc.org/About/Features)

## RemoteDesk 的实测结果

**这组灰色小字保住 1080p 的收益，大于更换放大方式。** 在 1080p 原生绘制 60 行 13、15、18 像素的中文和代码，用相同的 H.264 NVENC 参数传输。额外制作一条先缩到 720p 的对照流。两条都经过 RemoteDesk 硬解并放大到 4K。另用双倍字号在 4K 重绘同一页作为参考。

| 传到查看端的视频 | 查看端放大方式 | 与 4K 重绘参考的灰色笔画重合度 |
| --- | --- | ---: |
| 1280×720 | Windows 默认文字放大 | 0.516 |
| 1920×1080 | 系统缩放 | 0.558 |
| 1920×1080 | Windows 默认文字放大 | 0.573 |

重合度取灰色字笔画像素交集与并集的比值。它反映这张样图的笔画形状，人的阅读速度和辨字准确率需要另测。720p 是实验主动设置的对照。[查看三种画面的原尺寸裁图](clarity-samples/1080p-on-4k.png)

**编码会影响彩色代码，也会影响部分黑字。** Windows ClearType 会用红、绿、蓝子像素绘制字边。在第二张样图中，用 Windows GDI+ 实际绘制白底黑字，112,770 个笔画像素里有 85,180 个的 RGB 通道相差超过 12 级。[微软 ClearType 说明](https://learn.microsoft.com/en-us/typography/cleartype/)

用 NVENC 生成 H.264 4:2:0 和 High 4:4:4 两种单帧，再用同一 FFmpeg 解码和 BT.709 转换比较。选择压缩后大小接近的一对，在笔画及一圈相邻像素上比较平均色度误差，值越低，字边颜色越接近编码前。

| 样图 | 4:2:0 帧大小 | 4:4:4 帧大小 | 4:2:0 色度误差 | 4:4:4 色度误差 |
| --- | ---: | ---: | ---: | ---: |
| 第一张样图中的彩色文字 | 146,577 B | 143,945 B | 7.21 | 3.08 |
| Windows ClearType 黑字 | 265,095 B | 271,208 B | 12.95 | 4.01 |

这是静态帧对照。为匹配帧大小，4:4:4 样本使用了更高的量化参数，ClearType 样本的亮度误差也从 2.12 升到 3.26。Windows 端当前的 MF/D3D11 硬解收到了 4:2:0 帧，但在本机测试第一张 High 4:4:4 样图时返回了 `E_FAIL`。加入真彩前，需要用实际编解码样帧协商两端能力。[查看 Windows 黑字裁图](clarity-samples/cleartype-on-4k.png)

**现有无损补清可以补回编码损失。** 对第一张图又使用 RemoteDesk 自己的 Windows MF 硬编、硬解、图块压缩、分片重组和 GPU 合成。取同一底帧中的 1536×256 区域，24 个原始 RGB 图块合成后，4K 区域内的每个像素都和 1080p 原图整倍放大一致。范围外逐像素比较也一致。这批图块的压缩数据为 48,875 字节，在 4096 字节分片下加上图块头和外层记录开销共 52,384 字节，另需视频和网络传输开销。[查看同一帧补清前后](clarity-samples/native-tiles-on-4k.png)

原样放大会保住颜色和细线，也会放大低分辨率下的斜边台阶。同一批图块改用双线性采样，字边更平滑，但会混合相邻像素。4K 由应用重新绘制的文字保留了更多笔画形状。[查看两种图块采样与 4K 重绘](clarity-samples/native-edge-sampling.png)

## 对 RemoteDesk 的取舍

1. 办公桌面的第一优先级是保住远端已经绘制的 1080p 像素。判断一条会话时，同时记录远端桌面尺寸、实际编码尺寸和本地显示区域，再决定该调整传输还是显示。
2. 运动时继续用低延迟 H.264。停下后，有带宽余量才补原始像素。新版 Windows 的“画面 → 静止时补清文字”覆盖可见区域，1920×1080 有 135 个图块，较大桌面优先补中心附近的 144 块。两端都会协商新版能力，连接旧端时仍可使用此前的鼠标附近补清。
3. 全屏 4:4:4 适合作为两端都验证过硬解的能力。对于希望字形和本地 4K 排版一样细腻的使用场景，可以另行比较远端虚拟 4K 桌面配合 200% 显示缩放，让应用直接用更多像素画字。

竞品对照使用厂商公开文档，其会话内部采用的参数未知。上述像素测量使用 Windows 硬解和硬件显示窗口。

Windows 查看端的“画面 → 静止时补清文字”默认为“自动”。两端支持可见区域补清、连续两次显示统计都达到 20 Mbps 且硬解显示顺畅时，停手后开始补清。菜单也可以为本次会话选择“开启”或“关闭”。被控端另用接收回执限制实际发送量，输入和基础 H.264 画面优先。静止桌面本来就用很少带宽，判断网络拥塞还要看接收回执。[实时媒体拥塞控制要求](https://www.rfc-editor.org/rfc/rfc8836.html#section-2)

## 整张 1080p 办公桌面补清后能保留多少细节

在 RTX 2080 Ti 上回放 RemoteDesk 硬编的同一帧中文和代码，把 135 个原尺寸图块压缩、分片、重组，再由实际查看端的 D3D11 合成器放大到 3840×2160。将窗口输出与 1080p 原始像素直接放大两倍逐像素比较。普通 H.264 加文字放大时，8,294,400 个像素里有 2,891,320 个 RGB 完全相同。整页补完后，8,294,400 个均相同，包括窗口四角。[打开补清后的完整 4K 截图](clarity-samples/full-1080p-on-4k.png)

这张样图的 RGB 压缩数据共 199,428 字节。用 256 字节分片发送，共 856 片，连同应用协议头和加密记录共 303,004 字节，另有网络层开销。这里测量的是所有图块到齐后的结果。公网使用时每收到一块即可显示，复杂照片或没有带宽余量的线路会更慢。

开启补清，用同一张图在本机加密 TCP 连接上做三轮限速对比。100 Mbps 和 8 Mbps 两组的 H.264 基础流分别为每秒 34 帧和 6 帧，每组用相同输入对比新旧策略。100 Mbps 时整页补齐的中位数从 2.40 秒缩短到 1.29 秒，记录数从 856 降到 472，接收端逐块校验了原始像素。8 Mbps 时三轮均沿用小分片。把已经升档的链路从 100 Mbps 降到 8 Mbps，额外预算在约 0.12 秒内撤回。整页计时从允许发送补清图块开始，到接收端集齐并校验 135 块为止。

## 滚动和中文输入的实测

两个 Windows 进程运行在同一台双屏电脑上。被控端采集 3840×2160 的测试桌面，H.264 视频传 1920×1080。直连使用加密 UDP，中继测试强制经公网服务器往返，后者的收帧回执 RTT 中位数为 693 毫秒。下表展示最后一轮，滚动每组 6 次，中文输入每组 12 次，停手至首块各观察一次。

| 路径 | 滚动到画面变化，关闭／开启补清 | 中文输入到被控端文字变化，关闭／开启补清 | 停手至第一块补清 |
| --- | ---: | ---: | ---: |
| 本机 UDP 直连 | 41／58 毫秒 | 13／11 毫秒 | 0.83 秒 |
| 公网中继 | 764／739 毫秒 | 361／361 毫秒 | 1.59 秒 |

滚动和输入均取中位数。直连两次开关都保住了原 UDP 通道，219 个带图块标识的视频帧全部经 UDP 到达。另一次中继复测中，单次滚动达到 1.37 秒。公网往返波动较大，无法据此推断补清能降低延迟。直连开启后本轮滚动中位数多了约 17 毫秒，补清继续保留为可选项。

实际会话可用仓库中的 `VideoQualityProbe` 复测。Windows 主屏显示测试页，副屏打开查看窗口，滚轮每次都会改变页面中央标记的颜色。探针从查看端的 GPU 纹理读取该像素，记录从发送滚轮到颜色变化的时间，结果写进输出目录的 `summary.json`。

```powershell
$ffmpeg = (Get-Command ffmpeg).Source
dotnet run --project experiments/VideoQualityProbe -c Release -- --text-clarity $ffmpeg artifacts/clarity-fixtures
dotnet run --project experiments/VideoQualityProbe -c Release -- --native-detail-host artifacts/clarity-fixtures artifacts/clarity-direct
```

公网复测使用同一张测试页。将第二条命令中的 `--native-detail-host` 改为 `--native-detail-host-relay <已配置的中继地址>`，另选一个输出目录。探针要求显式指定的服务器与本机已保存配置相符，并在测试结束时断开临时节点。
