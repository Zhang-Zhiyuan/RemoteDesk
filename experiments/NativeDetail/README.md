# Native detail core and probes

The shared core lives in `src/RemoteDesk.NativeDetail`. Windows host/viewer
sessions now negotiate availability and expose a separate, off-by-default UI
switch. Existing upscaling/video defaults are unchanged. See the current
[production host qualification](../../docs/NativeDetailHost-20260914.md).
The CPU experiment below remains a historical control, not the production source.

The experiment keeps the current downscaled video as a base and sends stable,
native RGBA tiles for a requested viewport. It tests whether original text pixels
can arrive without leaving old text over a newer base. See the
[measured result](../../docs/NativeDetail-20260914.md).

The Windows viewer can now compose received tiles through its real decoder and
GPU presentation path in an opt-in qualification session. Separate GPU and owned
live-capture probes are described in the [video probe README](../VideoQualityProbe/README.md)
and [session audit](../../docs/NativeDetailSession-20260914.md). The original
`--native-details` command below remains the CPU composition control.

## Run

The core and unit tests require .NET 8, without a GUI or GPU:

```powershell
dotnet test experiments/NativeDetail.Tests/NativeDetail.Tests.csproj -c Release
```

The visual/transport probe requires Windows, NVENC-capable FFmpeg, MF/D3D11 and
the synthetic fixtures generated by `--text-clarity`. Choose new output paths:

```powershell
dotnet run --project experiments/VideoQualityProbe -c Release -- --text-clarity <ffmpeg> artifacts/text-fixture-new
dotnet run --project experiments/VideoQualityProbe -c Release -- --native-details <ffmpeg> artifacts/text-fixture-new artifacts/native-detail-new
```

An existing fixture can be reused. The probe refuses an existing output
directory. It uses a private ephemeral TCP listener on `127.0.0.1`, a random
per-run secret and the product's RDK1 authentication/AES-GCM record transport.
No real host is contacted and no desktop is captured or input injected. The
base video is decoded/presented through actual MF/D3D11/NIS to a hidden owned
window and read back. Final tile composition is CPU RGBA, not a production GPU
overlay. The comparison PNG contains unscaled source-pixel crops.

`interop-vectors.txt` contains C#-generated input events, expected results,
cache-pixel/state hashes and pending-byte counts. Independently implemented
Python and Java receivers check these values:

```sh
python3 -B experiments/NativeDetailInterop/native_detail_receiver.py artifacts/native-detail-new/interop-vectors.txt
```

```powershell
javac --release 8 -d artifacts/native-detail-new/java experiments/NativeDetailInterop/NativeDetailReceiver.java
java -cp artifacts/native-detail-new/java NativeDetailReceiver artifacts/native-detail-new/interop-vectors.txt
```

Python needs only its standard library. The Java test runs on a desktop JVM,
not Android. For Linux hardware validation, copy just the Python script and
vectors to an owned temporary directory and run the same command there.

## Correctness contract

Each state object has a single owning thread. All timestamps are monotonic
milliseconds on that owner's local clock; they are not synchronized wall clocks.

- `DetailSource.Observe` must receive exactly the native snapshot used to encode
  the corresponding base video, before downsampling or 4:2:0 conversion. A
  separate screenshot taken at a similar time does not satisfy this contract.
- Every base carries a complete manifest: session epoch, viewport request,
  dimensions, source sequence and per-tile content versions. Versions change on
  any native-byte change, even with no mouse or keyboard activity. A tile must
  stay unchanged for at least 250 ms before `Build` returns it.
- The receiver validates a manifest before decoding, then commits it and the
  new base presentation as one render transaction. Network arrival alone must
  not authorize an overlay. Changed tiles disappear; unchanged native tiles
  survive repeated lossy video/IDR updates.
- Future, obsolete, wrong-context and outside-viewport transfers are rejected.
  A changed tile's delayed old transfer cannot restore old text. Manifests are
  self-contained, so a dropped base does not break a delta metadata chain.
- Input invalidates details and requires a newer reference. Changing viewport,
  monitor, dimensions, session or enabling again needs a locally authorized
  reset with a newer epoch/request. An incoming packet cannot enable the mode.
  Disabling clears state without changing the base video or its geometry.

The current source compares/copies the full native CPU frame. This verifies
correctness, not zero-copy capture performance. There is no text detector,
perceptual change threshold or invented glyph reconstruction.

## Experimental wire format

All integers are little-endian. Epoch/request/sequence/version are positive
signed 64-bit values, portable to Java `long`. `NDL1` is an inner payload, not
standalone session authentication. All records require an authenticated, encrypted outer transport; the
SHA-256 below detects corrupt or mixed fragments and is **not authentication**.

Common header:

| Offset | Bytes | Meaning |
| ---: | ---: | --- |
| 0 | 4 | ASCII `NDL1` |
| 4 | 1 | Kind: 1 manifest, 2 large tile fragment, 3 small tile fragment |
| 5 | 3 | Reserved, must be zero |
| 8 | 8 | Epoch |
| 16 | 8 | Viewport request token |
| 24 | 4 | Native width |
| 28 | 4 | Native height |
| 32 | 8 | Base sequence / transfer's reference sequence |

A manifest appends a 32-bit run count at offset 40 and 10-byte runs at offset 44:
`uint16 tileCount, int64 version`. Runs must cover every tile exactly. The
128-pixel tile grid is row-major and edge tiles are cropped, not padded.

A fragment appends `int32 tileId` at 40, `int64 version` at 44, `int32 totalBytes`
at 52, `int32 offset` at 56, `int32 payloadBytes` at 60, and a 32-byte SHA-256 of
the complete compressed tile at 64. Data starts at 96. Offsets must be multiples
of 4,096 for kind 2 or 512 for kind 3; only the final fragment can be shorter.
Layouts cannot mix within one assembly. Pixel data is a **single zlib
member of lossless RGBA8**, not PNG and not NV12. Uncompressed size must exactly
equal the tile's native width × height × 4.

The probe's private base envelope is `NDB1`, a 32-bit manifest length, a manifest,
then one configured H.264 IDR. It travels as an opaque `VideoFrame` record on
the probe's own endpoint; it is **not** the production video payload layout.
Fragments use opaque `Control` records there. That original proof profile is
unchanged. The opt-in Windows session uses capability bit 26 and distinct RDK1
types 7 (atomic `NDV1` base/manifest), 8 (`NDL1` fragment), and 9 (`NDR1` local
request/stop). Type 7 has a 12-byte header: magic, int32 manifest length, int32
video length, followed by the manifest and standard 32-byte video header/AU.
Type 9 is exactly 48 bytes: magic, enabled byte, three reserved zeros, int64
epoch/request, int32 native width/height and int32 viewport x/y/width/height.
It is sent only when both peers explicitly support this tier. Types 10/11 carry
72-byte receiver feedback and a 24-byte availability offer. Types 12/13 carry a
56-byte authenticated UDP-video resume boundary/acknowledgement after explicit
off; new native video itself stays on reliable transport. Old peers keep the
existing record types. `NativeDetailSessionProtocol` defines the strict layouts.

## Bounds and scheduling

| Resource | Limit |
| --- | --- |
| Native dimensions | Each 1–8192; at most 16,777,216 pixels and 2,048 tiles |
| Retained source RGBA | At most 64 MiB |
| Compressed tile | 96 KiB |
| Fragment | 4,096 data bytes + 96 header + 25 RDK1 record bytes |
| Incomplete receiver transfers | 2, at most 192 KiB compressed storage |
| Incomplete transfer lifetime | 1,500 ms, checked on subsequent receive |
| Decoded receiver cache | 64 tiles, at most 4 MiB RGBA |
| Sender queue | 64 tiles and 256 KiB compressed data |
| Sender burst credit | At most one maximum wire fragment: 4,217 bytes |

The sender uses a caller-supplied available bitrate, includes wire overhead in
its token bucket, yields to pending control and pauses when the reported send
queue reaches 50 ms. Interaction cancels queued work. Each chunk rechecks tile
currency; obsolete or aged work is discarded. Bounded credit survives a control
message so frequent control traffic with coarse timers cannot starve details.
This is not a bandwidth estimator and does not remove TCP head-of-line blocking.

Receivers bound allocations before assembly/inflate, verify hashes, reject
conflicting duplicate fragments, and reject trailing/concatenated zlib members,
truncation and excess output. .NET 8 can silently finish truncated zlib input
after producing all pixels; the core's guarded input stream checks exact member
termination, including its trailer. Python and Java separately check their
inflater's completion and unconsumed-input state.

## What the measurements do not establish

The probe configures a 2 Mbps detail budget and synthetic priority control
requests; it does not measure spare WAN capacity. Delivery timing excludes the
250 ms stability wait, capture/encode setup and final display composition. The
next delivery phase can begin with up to one fragment of retained credit.
Control timing is one encrypted local write/read completion, not round-trip
network delay or an applied mouse/keyboard acknowledgement.

This original CPU probe covers no continuous competing video, real relay, real
input, production UI, DWM/photon latency, HDR, fractional DPI, phone Surface or
sustained thermal test. The separate GPU probe covers fractional output geometry,
not actual multi-monitor DPI transitions or Android display hardware.
The separate production host now handles backend selection, coarse-damage
refinement and receiver-feedback admission. Cross-platform native capture/UI
remains unimplemented. See the current host audit above. The FFmpeg WGC/DDA host exposes an
encoded stream; an unrelated CPU screenshot must not be treated as its source.
